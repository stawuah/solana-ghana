# solana-ghana

Solana Ghana Community website — a colorful, Ghana-first on-ramp for builders to learn, build, connect, and contribute.

## Run locally

```bash
npm install
cp .env.example .env.local   # fill in the values
npm run migrate              # create the tables
npm run dev
```

Production verification:

```bash
npm run build
npm run start
```

The project includes the Home, Learn, Courses, Build, Ambassadors, Security, Events, and Community experiences. Course content is grounded in the [rssol-memory curriculum](https://github.com/stawuah/rssol-memory).

## Backend

Three public forms post to Next.js route handlers, which store the submission in Postgres and then notify the organisers by email.

| Form | Endpoint | Table |
| --- | --- | --- |
| Newsletter signup | `POST /api/signup` | `signups` |
| Team application | `POST /api/applications/team` | `team_applications` |
| Ambassador application | `POST /api/applications/ambassador` | `ambassador_applications` |

Every endpoint runs the same pipeline (`lib/submit.js`): honeypot check, per-IP rate limit, field validation, insert, then notify. Email is deliberately the last step and is non-fatal — once the row is written the submission is safe, so a mail outage never shows the applicant an error.

Responses are `{ ok: true }` on success, `400` with a per-field `errors` object on invalid input, `429` when rate limited, and `500` if the insert fails. A repeat signup returns `{ ok: true, duplicate: true }` so signing up twice is harmless.

### Storage

Neon Postgres, reached with `pg` over a pooled connection. Migrations are plain SQL in `db/migrations/`, applied in filename order by `npm run migrate`. They are written to be safe to re-run.

Raw IP addresses are never stored. Submissions keep a salted SHA-256 prefix (`IP_HASH_SALT`) so repeat submitters can be recognised during abuse review without holding personal data.

### Email

Resend, via `lib/mail.js`. Each submission sends the organisers the full content with the applicant in `reply_to`, and sends the applicant a confirmation.

**Resend only delivers from a verified domain.** Until one is verified, the shared `onboarding@resend.dev` sender can reach the Resend account owner and nobody else, so applicant confirmations are skipped rather than silently bounced. They are gated behind `RESEND_VERIFIED`:

1. Verify a domain in Resend.
2. Set `RESEND_FROM` to an address on it.
3. Set `RESEND_VERIFIED=true`.

Applicant mail starts sending with no code change.

### Rate limiting

`lib/rate-limit.js` keeps a per-IP sliding window in process memory: 5 submissions per endpoint per 10 minutes. The site runs as a single Render instance, so one process sees every request and this is sufficient. **If the service is ever scaled past one instance, each instance keeps its own counts and the effective limit multiplies** — move the counter to Postgres or Redis before scaling out.

### Environment

See `.env.example`. On Render these are set in the dashboard; `render.yaml` marks them `sync: false` so they are never committed. `IP_HASH_SALT` is generated by Render automatically.
